1. How the schema is organised

  • Legacy origin. Most tables come from the previous PHP system and keep their names, keys and tinyint flags. New features (messaging, proposals, media, chatbot, notifications) use newer tables with Laravel conventions (id, created_at, updated_at).
  • One account, many profiles. A person has one user_account. Each of the four profile tables links back to it through user_id, so one account can own several profiles of different types.
  • Polymorphic profile references. Tables that can point at any profile type store a pair: profile type + profile id. Two encodings exist:
Profile typeNumeric codeStringTable · primary keyStatus column (1 = active)
Business1businessprofile_business.business_idbusiness_profile_status
Investor2investorprofile_investor.investor_idinv_profile_status
Mentor4mentorprofile_mentors.mentor_idmentor_profile_status (+ deleted_at)

Numeric codes are used by user_profiles, profile_visitors, online_payments and profile_memberships. String names are used by profile_contact_conversations, profile_proposals and profile_media.

No foreign keysThe legacy schema has no database-level foreign keys. Every relationship below is logical: the application joins on it and checks it in queries (for example, ownership is always filtered by user_id). Deleting rows by hand can leave orphans, so delete children first.

2. Relationship diagram (active tables)

Gold lines are logical relationships (no database constraint). Not drawn, to keep it readable: reference data (industry_categories, ind_pref_business, bx_cities), content (bx_articles → bx_author, articles_comments) and framework tables. They are all listed in section 4.

5. Why these indexes

IndexQuery it serves
profile_* (status, created_at, id)Directory listings and home sliders: "active profiles, newest first", paginated.
profile_* (user_id)Dashboard: "my profiles", and every ownership check.
profile_startups (status, industry_sector)Startup listing filtered by industry.
ind_pref_business (business_profile_id, profile_status, parent/sub category)Business industry filter and home industry counters.
industry_categories (parent_id, category_status)Building the category tree for filters and the footer.
conversations (owner_user_id, updated_at) and (sender_user_id, updated_at)Inbox: "my conversations, most recent first" for either side.
messages (conversation_id, id) / (conversation_id, created_at)Loading a thread, newest messages, latest message per conversation, unread counts.
conversation_reads PK (conversation_id, user_id)One marker per user per thread; makes the read update an atomic upsert.
proposals (sender|recipient_user_id, status, created_at)"Proposals sent / received" lists with the status filter, newest first.
profile_media (user_id, profile_type, profile_id)Media for one owned profile; owner checks on download.
profile_visitors (profile_type, profile_id)Dashboard view counts. Verified with EXPLAIN: full scan of 5,000 rows → 2 rows.
articles_comments (article_id, comment_status, created_at)Approved comments for one article, newest first. EXPLAIN: 5,000-row scan + filesort → ~25 rows.
bx_articles (status, created_at|views|comments, id)Article list sorted by newest, most viewed or most commented.
online_payments UQ order_no, UQ razorpay_payment_id, IX udfLook-ups by order number and Razorpay order id; the unique keys also stop one payment being applied twice.
profile_memberships (user_id, profile_type, profile_id)Deactivating the previous membership and showing My Plan.
UQ user_account.email, businessex_newsletter.emailPrevent duplicate accounts and subscriptions; fast login look-up.
Not indexed on purposeFree-text search uses LIKE '%term%' across several columns, which a normal index cannot speed up. If search becomes slow as data grows, add FULLTEXT indexes or a search engine instead of more B-tree indexes.

7. Recommendations

  • Add foreign keys gradually, starting with payments, memberships, messaging and proposals, after removing orphaned rows.
  • Use one profile-type encoding. New tables use strings (business), older ones numeric codes; pick one for future tables and map the other.
  • Store money as DECIMAL: online_payments.amount, profile_memberships.amount and membership_plans.plan_amount are strings today.
  • Keep profile_visitors small: count one view per viewer per profile per day, or aggregate old rows.
  • Archive or drop legacy tables once confirmed unused, to reduce backup size and confusion.
  • Every schema change goes through a migration that runs on MySQL and SQLite and has a working rollback; run php artisan migrate (it also refreshes the app's schema cache).
