1. Project overview

BusinessX (BusinessX – World Trade Council) is a UK marketplace that connects four kinds of members:

Profile typePurposeLegacy codeTable
BusinessBusinesses for sale, seeking investors or loans1profile_business
InvestorIndividuals and firms looking to invest or acquire2profile_investor
MentorAdvisers offering expertise4profile_mentors
StartupEarly-stage companies raising funds7profile_startups

Visitors browse public directory listings and profile pages. Members register one or more profiles, contact other profiles, hold conversations (with real-time live chat), exchange proposals with attachments, and can buy a paid membership (Premium or Gold) through Razorpay to gain priority placement.

Main capabilities

Public site

Home page with sliders and counters, four directory listings with filters, public profile pages, articles and comments, static pages, pricing, newsletter with double opt-in, keyword chatbot.

Accounts & registration

Multi-step registration wizard per profile type, quick registration, email verification, first-time password setup, login, password reset.

Member dashboard

Account details, password, profile management, inbox and live chat, proposals sent and received, instant auto-response, activity notifications, My Plan.

Payments

Guest checkout from the pricing page (claimed at registration), and My Plan upgrades for existing profiles. Server-side verification plus a signed webhook.
Legacy schema The database descends from an older PHP system. Most tables keep their legacy names and columns (for example user_account with primary key user_id, numeric profile-type codes, and tinyint status flags). Code therefore uses the query builder (DB::table()) far more than Eloquent models. Keep this in mind before renaming anything.

Application layers

Controllers
app/Http/Controllers. Listing pages share AbstractListingController (search, location, industry, amount ranges, membership priority, sorting, card building). DashboardController holds most member features.

Services
app/Services/Payments: RazorpayGateway (API + signatures) and MembershipPaymentService (idempotent completion, claims, membership records).
Support
app/Support/SchemaCache (cached Schema::has*), app/Support/PublicContentCache (home page and footer data).
Models
Mostly thin legacy models. The ones in active use: UserAccount (auth model), ProfileMedia, plus notifications via Laravel's notifications table.
Events & notifications
ConversationMessageSent (broadcast), DashboardActivityNotification (database + mail, queued after commit).
Views
resources/views: layouts, pages (public), dashboard, static, emails, components, errors.

Key design decisions

  • Query builder over Eloquent. Legacy tables are queried with DB::table(). Profile types are described by arrays (table, id column, status column, title columns) in AuthController, DashboardController::PROFILE_TYPES and MembershipPaymentService::PROFILE_TABLES.
  • Optional legacy tables/columns. Code checks SchemaCache::hasTable()/hasColumn() before using some tables, so partially migrated databases (and focused tests) keep working. Use SchemaCache, never the Schema facade, in request code: the facade queries information_schema on every call.
  • Authorization by ownership in queries. Every lookup of a member-owned record filters by the signed-in user and answers 404 (not 403) when nothing matches, so responses do not reveal whether a record exists.
  • Configuration-driven registration. config/registration_profiles.php defines every wizard step and field per profile type; validation rules are generated from it.

5. Local development setup

Prerequisites

  • XAMPP (Apache + MySQL/MariaDB) with PHP 8.2+, extensions: pdo_mysql, mbstring, openssl, gd (with WebP), fileinfo, curl.
  • Composer 2, Node.js 20+ and npm.
  • Optional: AWS S3 bucket and credentials (uploads), Razorpay test keys (payments), SMTP account (mail).

First-time setup

# 1. Dependencies
composer install
npm install

# 2. Environment
copy .env.example .env          # then fill in DB, mail, AWS, Reverb, Razorpay values
php artisan key:generate

# 3. Database (create the MySQL database first)
php artisan migrate
php artisan db:seed --class=TestimonialSeeder      # optional demo data
php artisan db:seed --class=ProfileRecordsSeeder   # optional demo profiles

# 4. Frontend assets
npm run build

Running the app

On XAMPP the site is served from http://localhost/businessX-uk-html-mockup/public (this is APP_URL). For the full development stack (built-in server, queue worker, log tail, Vite and Reverb together) use:

composer dev
# runs: php artisan serve | queue:listen | pail | npm run dev | reverb:start --port=8081

If you only use Apache, still run these in separate terminals when you need them:

php artisan queue:work            # queued mail and notifications
php artisan reverb:start --host=127.0.0.1 --port=8081   # live chat
Tip: queued jobs Verification emails, password resets and activity notifications are queued. Without a worker they sit in the jobs table. Locally you can set QUEUE_CONNECTION=sync to send immediately.

7.2 Registration & authentication

The auth model is App\Models\UserAccount (table user_account, key user_id) on the standard web session guard. Passwords use Laravel's hashed cast (bcrypt).

  1. Register. Full wizard (/register/{type}) or homepage quick registration (/register/quick). Creates user_account (no password yet), the profile row, user_profiles mapping and stored uploads in a transaction. A signed-in member can add further profiles from the dashboard without a new account.
  2. Verify email. A queued email carries a signed link (60 min). Verifying redirects a password-less account to the set-password page.
  3. Set password. Signed link, valid only while the account still has no password (single use). Inactive accounts are refused.
  4. Login. Throttled 5 attempts per email+IP; requires a verified email and an active account; session regenerated.
  5. Password reset. Laravel password broker (hashed, single-use, 60-minute tokens). A successful reset ends every stored session of the account.
Validation rules to know Full registration requires UK mobiles in 07XXXXXXXXX format, rejects example.com, sample.com and test.com addresses, requires city fields to match bx_cities, and validates UK postcodes. Uploads: max 1 MB, extension allow-list from the config, image dimension limits. Passwords (reset/setup): at least 8 characters with letters and numbers; the dashboard change form also requires a symbol.

7.3 Profiles & media

  • Uploads are stored on S3 under profiles/{type}/images|documents/Y/m/{uuid}.{ext}. The extension comes from the file content, never the client name.
  • Images are public (served from S3 or IMG_CDN). Documents are private and only served through /profile-media/{id}/download (owner only) as a 5-minute signed S3 URL.
  • Every upload is recorded in profile_media; the profile row keeps the current URL in its legacy column (for example seller_prof_pic).
  • Owners edit profiles at /dashboard/profiles/{type}/{id}/edit; ownership is enforced in the query.

8. Payments (Razorpay)

Prices are fixed on the server in MembershipPaymentService::PLAN_AMOUNTS (pence, GBP). The client never supplies an amount.

PlanMonthlyAnnualProfile membership_plan code
Premium£29.00£299.001
Gold£89.00£999.002

Flow

1. InitiatePOST .../payment/initiate creates a Razorpay order (15 s timeout) and an online_payments row, status 0
→
2. CheckoutRazorpay Checkout in the browser (card / UPI)
→
3. VerifyPOST .../payment/verify checks the HMAC signature, then complete()
→
4. WebhookPOST /webhooks/razorpay (payment.captured, order.paid) as the safety net

Two entry points

  • Guest checkout (/pricing): the payment is created with profile_id = 0. After verification the browser is sent to the registration wizard with payment_order_no. Registration claims the payment for the new profile only if the order was verified in the same session or the account email equals the payer email. The claim is atomic (row lock + profile_id = 0 guard).
  • My Plan upgrade (/dashboard/my-plan): ownership of the profile is checked first; on completion the profile gets membership_paid = 1 and its plan code, the previous active profile_memberships row is deactivated and a new one (1 month or 1 year) is inserted.

Guarantees

RiskHow it is handled
Replay of a valid signaturecomplete() locks the payment row and returns early if it is already SUCCESS; razorpay_payment_id is unique.
Webhook and browser both arriveSame idempotent complete(); whichever is second is a no-op.
Browser closed after captureWebhook activates the plan.
Forged or wrong amount in webhookHMAC check with RAZORPAY_WEBHOOK_SECRET; amount and currency must match the stored order.
Bad signature on a paid orderOnly INITIATED payments can be marked FAILED.
Partial writesStatus, profile and membership updates run in one transaction.

Statuses in online_payments.payment_status: 0 initiated, 1 success, 2 failed. udf holds the Razorpay order id. The webhook route is exempt from CSRF in bootstrap/app.php because Razorpay cannot send a token; its HMAC signature replaces it.

Razorpay dashboard setupCreate a webhook pointing to https://<your-domain>/webhooks/razorpay with events payment.captured and order.paid, and put its secret in RAZORPAY_WEBHOOK_SECRET.

Indexes added for the workload

  • Listings and search: status + created_at + id per profile table, user_id, startup industry, category parent, article status orders.
  • Messaging: conversation owner/sender + updated_at, messages by conversation, proposals by sender/recipient + status + created_at.

  • Comments (article_id, comment_status, created_at) and profile visitors (profile_type, profile_id).

Migration rules

  • Never edit a migration that has run anywhere; add a new one. Every migration must run on MySQL and SQLite (tests run all of them).
  • Provide a working down(). Check data before adding unique keys (see 2026_10_13_000001 for the pattern).
  • Running migrations automatically clears the schema cache (SchemaCache listens to MigrationsEnded).
  • There are no foreign keys in the legacy schema; integrity is enforced in code. Add constraints only after cleaning orphaned data.

11. Security model

ConcernImplementation
Web root exposureProduction must serve public/ only. On XAMPP the root .htaccess denies .env, .git, storage, vendor, app, config and tooling files (verified 403).
AuthenticationSession guard, bcrypt via the hashed cast, login throttling, session regeneration on login, invalidation on logout, verified + active account required.
Account recoveryBroker tokens (hashed, single-use, 60 min); single-use set-password link; reset and password change end all sessions; no user enumeration in messages.
Authorization / IDOREvery member-owned lookup is filtered by the signed-in user and returns 404 otherwise; broadcast channel limited to conversation participants; media downloads owner-only.
CSRFEnabled for all web routes; the only exception is the HMAC-verified Razorpay webhook.
Validation & mass assignmentValidated arrays only; no $request->all(); status/amount/activation fields are not fillable on models.
SQL injectionQuery builder bindings everywhere; raw fragments use hard-coded column names; sort and filter values are allow-listed.
XSSBlade escaping; the only unescaped output is article HTML passed through a DOM allow-list sanitiser and hard-coded static-page content.
UploadsSize limits, extension allow-lists, image dimension limits, UUID names, extension from content, private documents via short-lived signed URLs.
Rate limitingLogin, reset, verification, registration, contact, comments, replies, proposals, payments, chatbot, newsletter, city suggestions.
PaymentsServer-side amounts, HMAC signature checks with hash_equals, idempotent completion, webhook amount/currency check.
SecretsOnly in .env (untracked); no secrets in logs or responses; Razorpay errors logged by message only.
Rules for new code
  • Never disable CSRF, validation or ownership checks to make something work.
  • Scope every query for member data by Auth::id() and answer 404 when nothing matches.
  • Add a throttle middleware to any new endpoint that sends email, writes data publicly or calls an external API.
  • Store uploads on S3 with generated names; never trust the client filename or MIME type.

Performance rules for new code

  • No queries inside loops: batch with whereIn() + keyBy() (see profileConversationLabels()). DashboardQueryCountTest fails if list pages start growing with their rows.
  • Paginate or cap every list (listings 12, articles 9, proposals 15, comments 50, thread messages 100).
  • Use SchemaCache, not Schema, in request code.
  • Select the columns you need on large tables; check new filters with EXPLAIN before adding indexes.
  • Call external APIs with explicit timeouts, and queue slow work (mail is already queued).
  • If you add public, visitor-independent data to the home page, it is cached; clear PublicContentCache wherever that data is written.

Frontend

  • Vite bundles only resources/js/app.js (live chat, about 81 KB / 23 KB gzip) and resources/css/app.css; loaded on dashboard pages.
  • Page styles and scripts are plain files in public/css and public/js, cache-busted with ?v= query strings.
  • Keep images at display size (default profile images are 600 px wide).

Definition of done for a change composer test, composer analyse and composer format:check all pass, new behaviour has a feature test (including the unauthorised / invalid case), and migrations run up and down.

How the tests are built

  • Environment from phpunit.xml: SQLite in memory, array cache and session, sync queue, array mailer, broadcasting off.
  • Many older tests create only the tables they need with Schema::create() in setUp(). Newer tests run the real migrations ($this->artisan('migrate')), which is preferred because hand-written schemas drift from production.
  • Use Mail::fake(), Http::fake() (Razorpay API) and Storage::fake('s3'); never call real services.
  • Payment tests sign callbacks with a test secret through hash_hmac('sha256', ...).

14. Coding conventions

  • Formatting: Laravel Pint (PSR-12 based Laravel preset). Run composer format before committing.
  • Types: parameter and return types on new methods; generics in docblocks for collections (Collection<int, \stdClass>).
  • Controllers stay thin: HTTP concerns only. Put multi-step business logic in app/Services (see payments) and validation in Form Requests (app/Http/Requests).
  • Transactions: wrap multi-table writes in DB::transaction(); use conditional updates or lockForUpdate() for anything that can race; use upsert() instead of exists-then-insert.
  • Notifications and mail are queued; notifications sent inside transactions must use afterCommit() (already set on DashboardActivityNotification).
  • Profile type handling: reuse the existing type maps; do not hard-code table names in new places.
  • Comments explain why (constraints, legacy quirks), not what the next line does.
  • Commits: small, one concern each, imperative subject line, body explaining the reason and any behaviour change. Formatting-only changes go in their own commit.
  • Branches: work on feature branches off development; merge to main through pull requests.

15. Deployment checklist

Server

  • Web server document root points to public/ (do not rely on the root .htaccess in production).
  • HTTPS everywhere; APP_DEBUG=false; SESSION_SECURE_COOKIE=true; LOG_LEVEL=warning.
  • storage/ and bootstrap/cache/ writable by the web user; nothing else writable.
  • Supervised queue worker (php artisan queue:work --tries=3) and Reverb (php artisan reverb:start) behind TLS.
  • Scheduler cron if scheduled tasks are added: * * * * * php artisan schedule:run.

Each release

  2. Set RAZORPAY_KEY_ID, RAZORPAY_KEY_SECRET, RAZORPAY_WEBHOOK_SECRET and create the webhook in Razorpay.

16. Troubleshooting

SymptomLikely cause and fix
Verification / reset emails never arriveNo queue worker running. Start php artisan queue:work or set QUEUE_CONNECTION=sync locally. Check failed_jobs.
"Online payment is not available yet"Razorpay keys missing from .env (then config:clear).
Webhook returns 503 / 400503: RAZORPAY_WEBHOOK_SECRET not set. 400: secret differs from the one configured in Razorpay.
Paid but plan not activeCheck online_payments status and webhook delivery logs in Razorpay; a guest payment is attached only when the payer registers.
Live chat says "Connecting..." foreverReverb not running, or VITE_REVERB_* differ from the server; rebuild assets after changing them.
Uploads fail with storage errorAWS credentials or bucket missing; run config:clear after fixing.
New column or table "not found" by the app after a manual DB changeSchema metadata is cached; run php artisan cache:clear (migrations clear it automatically).
Home page shows old profiles/articlesArticles/testimonials refresh within 5 minutes; run cache:clear to publish immediately.
Registration rejects a valid-looking cityCities must exist in bx_cities; add the city there.
Tests fail with "no such table/column"The test's hand-written schema lacks it; add it, or switch the test to $this->artisan('migrate').
